# br provider pin for the jot-review promotion step

Observed 2026-08-13. Jot wraps the `br` CLI, which carries no in-band version
negotiation, so the pin belongs here rather than with `br` — this repository
is the consumer of the unstable interface.

## The wrapped surface is one operation

`jot-review` invokes `br` at exactly one point: creating a bead when the
operator promotes a pending note.

```sh
br create --title "<title>" --type <type> --priority <n> \
          --description "<text>" --external-ref "<note id>"
```

`--external-ref` carries the pending note's id onto the bead, so a promoted
note can be traced back to its capture. Verified present on this version:

```
$ br create --help | grep external-ref
      --external-ref <EXTERNAL_REF>  External reference
```

Nothing else in Jot reads or writes the tracker. Earlier drafts of this record
also pinned `br --no-db show` for forward citations, and the `br list`
reconciliation read and comment surface; all three served checks
(`check_bead_citations`, `check_reverse_citations`) deferred out of the
docs-doctor port by `jot-met.3`, so they are not part of the wrapped surface
and are not pinned here.

**Verified independently today**, not copied: `sha256sum` of the installed
binary at `~/.local/bin/br` returns
`a3b59c6bde363efe251c28a7908d169f7b5671a22894e9577d253983750339e3`, matching
the `binary_sha256` recorded in the abacus-v1 provider lock
(`.abacus/providers.lock.toml`, `[providers.br]`), whose shape this record
follows. `br --version` reports `br 0.1.45`.

**Not verified:** the release asset sha256 is carried across from that lock.
The asset was not re-downloaded, so that row is inherited evidence rather than
an observation made here.

## Mismatch policy: fail-closed at promotion, not at startup

`br` is a declared dependency for **full function**, not a precondition for
starting. The split is deliberate and load-bearing:

- **`jot` capture requires no tracker.** It is pure filesystem plus `git
  rev-parse`, and it must keep working when `br` is absent — a capture that
  fails because a tracker is missing defeats the point of a three-second
  capture path.
- **`jot-review` promotion requires it.** A missing or mismatched binary
  there is an operator-visible failure at the moment of promotion. Because
  promotion is human-gated (north-star non-goal 5), there is no unattended
  path along which a provider mismatch could corrupt the tracker silently.

Verified today: with `br` absent from `PATH`, capture and listing both
succeed.

```
$ env -i PATH=/usr/bin:/bin python3 tools/jot.py "captured with no br on PATH"
noted → /tmp/…/.git/jot/pending/20260813T202923Z-3486222-d78e0f.json
$ env -i PATH=/usr/bin:/bin python3 tools/jot.py list
20260813T202923Z-3486222-d78e0f  2026-08-13T20:29:23.819116Z
    captured with no br on PATH

1 pending
```

## What would invalidate this record

A `br` upgrade. The pinned surface is one subcommand and one flag, so the
check on a new version is small: confirm `br create` still accepts
`--external-ref` with the same meaning, recompute the binary sha256, and date
a new record. Do not treat a passing `jot-review` run as evidence the pin
still holds — the operator gate means a human absorbs a broken invocation
before the tool notices.
